    What WCAG is

    WCAG 2.2 is the W3C's current WCAG 2 Recommendation. It organises accessibility into 13 guidelines under four principles and uses testable success criteria at levels A, AA and AAA. WCAG 2.2 adds nine success criteria over 2.1 and removes obsolete criterion 4.1.1 Parsing.

    1 · PerceivablePeople can get the information through senses and formats available to them.
    2 · OperablePeople can navigate and use controls with the input methods available to them.
    3 · UnderstandableContent and interactions are readable, predictable and forgiving.
    4 · RobustCode communicates reliably with browsers and assistive technologies.

    Important: passing an automated scanner is not WCAG conformance. Many criteria require human judgement, keyboard testing, zoom/reflow testing and assistive-technology checks.

    Readable text should not depend on perfect eyesight or perfect lighting.

    WCAG AA text: 4.5:1 for normal text; 3:1 for large text. AAA: 7:1 normal; 4.5:1 large. Important non-text controls and graphical objects generally need 3:1 under 1.4.11. WCAG has defined exceptions, so use the formal criterion for edge cases.

    Five-minute reality check

    Quick manual tests

    ⌨ Keyboard

    Put the mouse away. Use Tab, Shift+Tab, arrows, Enter, Space and Esc. You should reach, see and operate everything in a sensible order.

    🔎 Zoom & reflow

    Zoom to 200%, then test a narrow viewport / 400% equivalent. Content should remain readable and usable without losing controls or forcing horizontal-and-vertical scrolling for ordinary content.

    🎨 Remove colour

    Imagine the page in greyscale. Errors, selected states, charts and links must still make sense without colour being the only signal.

    🧭 Structure

    Check the page title, one logical heading hierarchy, landmarks, labels and meaningful link text. Visual size alone is not semantic structure.

    📝 Forms

    Every field needs a persistent accessible label. Trigger errors: the message should identify the problem, suggest a fix when known, and be announced where appropriate.

    🧩 Third parties

    Test cookie banners, payment widgets, chat, maps, calendars, CAPTCHA, video players and embeds. Your user experiences the whole journey, not just your own code.

    Often forgotten

    Documents, PDFs and content

    Accessible documents

    • Prefer an accessible HTML page when it can provide the same information.
    • Use real headings, lists and table headers; do not fake structure with font size or bold text.
    • Set document language and a meaningful title.
    • Add useful alt text to informative images and mark decorative images appropriately.
    • Make link text meaningful and check reading/tag order in exported PDFs.
    • Ensure form fields, if present, have labels, logical tab order and clear instructions.
    • Check colour contrast and never rely on colour alone.

    Editorial workflow

    • Write descriptive headings and concise link text.
    • Caption video; provide transcripts or audio description where the relevant criteria require them.
    • Describe charts in text, including the conclusion the chart is meant to communicate.
    • Avoid all-caps blocks, dense walls of text and unexplained jargon where simpler wording is possible.
    • Check social graphics: essential words embedded in images need an accessible equivalent.
    • Ask suppliers for accessibility evidence before buying a platform or widget.

    A practical testing stack

    LayerWhat to doFinds
    AutomatedRun axe, Lighthouse or another rules engine during development and CI.Some markup, names, contrast and structural failures.
    KeyboardComplete real tasks without a mouse.Focus order, traps, invisible focus, inaccessible custom controls.
    Zoom / reflowTest 200% text zoom and narrow/400%-equivalent layouts.Clipping, overlap, hidden controls, two-dimensional scrolling.
    Screen readerTest representative tasks with platform-appropriate assistive technology.Names, roles, states, announcements, heading/landmark structure.
    Content reviewReview alt text, labels, instructions, errors, links, captions and language.Meaning and clarity problems automation cannot judge.
    User testingInclude disabled people in research and task testing.Real barriers, workarounds and cumulative usability failures.

    Definition of done

    A feature is not done because it “looks accessible”. Include accessibility acceptance criteria, test the full journey, record known issues, assign owners and retest fixes. Recheck after design-system, CMS, payment, cookie, chat or other supplier changes.
